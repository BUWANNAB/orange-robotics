# 地图数据管理重构方案（待实施）

日期：2026-10-28。本文是代码审计与实施建议，尚未迁移业务数据库，也未连接 021。

## 本轮已完成

移除侧边栏“室内导航”，备用菜单也改为“地图与路线”。保留旧页面代码及雷达配置共用组件。

## 已核实的问题

1. 旧数据管理页调用 `data-admin/entities`、实体元数据与通用增删改接口。当前 FastAPI 后端没有这些接口。页面默认在网络错误或 404 后加载 `data-admin-mock.json`；该文件标注为 2026-09-15 的旧数据库抽样快照，模拟写入只保存在浏览器内存中。它不能充当当前系统的真实数据管理页。
2. 页面以表与列为中心，暴露原始字段、逻辑删除标记与复合实体明细。默认没有必选地图范围，多张地图混在同一列表。
3. 旧站点/路线使用 `t_station`、`t_route`、`t_route_detail`，地图归属靠名称字符串，路线站点列表存字符串，模型中缺少相应外键约束。新主页使用 `rds_map` 的草稿 JSON、发布版本和独立任务链表。两套数据不是同一个数据源。
4. 新地图使用全局唯一名称。删除是逻辑删除，创建时也查询已删除记录，因此删除地图后原名不能重新创建。此问题已在隔离数据库复现。
5. 旧站点新增按“相同地图名称 + 相同站点名称 + 未删除”查重，已删除站点不占用名称。此行为与地图名称占用问题不同。
6. 新主页删除站点时会移除相连路径；删除路径不删除端点。任务链仍按点位编号引用，执行时会验证已发布地图的点位和可达性。若删点后用相同编号创建新点，存在旧模板把新点视为原目标的设计风险，需通过稳定对象 ID 与引用影响检查解决。

## 页面方案

普通入口命名“地图数据”。顶部固定显示当前地图、草稿/发布状态与更新时间。默认继承地图主页选择；无地图时明确要求选择。切换地图后清除旧列表、选择和分页，忽略旧请求的迟到结果。

只显示所选地图下的业务对象：

| 分类 | 默认展示 | 常用操作 |
| --- | --- | --- |
| 站点 | 编号、名称、类型、XY、朝向、引用情况 | 搜索、在地图定位、编辑、删除 |
| 路线/路径段 | 起点→终点、方向、长度、速度、引用情况 | 在地图高亮、编辑、删除 |
| 区域 | 名称、类型、限速、覆盖范围 | 在地图高亮、编辑、删除 |
| 任务链 | 名称、起点、步骤数、循环次数、有效状态 | 查看步骤、编辑、停用/删除 |
| 版本记录 | 版本号、发布时间、操作人 | 查看、比较、受控回滚 |

不在日常页面显示数据库字段名、内部 ID、原始 JSON 或手工修改删除标记。设备参数和运行日志归设备/运维功能；旧数据迁移归管理员工具。“全部地图”仅作明确标记的跨图只读检索，每行必须显示地图归属，不提供跨图批量修改。

数据页与地图主页共用同一套服务、权限、草稿修订号与发布流程。保存草稿不改变在用发布版本。禁止后台接口不可用时自动显示快照并模拟保存；联调快照仅允许显式测试入口，始终醒目标注。

## 数据与标识方案

第一阶段复用 `rds_map` 和发布版本，不为一张数据列表复制一套业务表。按 `map_id` 读取草稿里的站点、路径和区域，按 `map_id` 查询任务链；变更经过统一的后端校验和修订号并发检查。

随后增量加入稳定的站点、路径、区域标识，站点编号与显示名称不再作为对象身份。路线端点及任务链引用稳定 ID；运行记录固定地图版本和快照。现有编号格式继续保留以兼容 ROS 协议。不能先改协议再要求设备跟随。

若后续数据量确实需要关系表查询，采用“地图 + 草稿/版本 + 站点 + 路径 + 区域 + 引用”的结构，所有业务对象带地图 ID；关系表或投影必须与地图文档事务一致，不能成为第二个可独立编辑的数据源。引用同地图约束由数据库及服务共同验证。

## 命名和删除规则

- 对象的数据库 ID、稳定对象 ID 永不复用。相同显示名称不意味着相同对象。
- 同一地图的有效站点编号唯一；不同地图可使用相同编号。名称可重用，但同图重名需在界面提示并同时显示编号。
- 删除站点后可使用原名称/编号新建，但生成新身份。旧任务链不得自动指向新站点；恢复旧对象时若名称/编号冲突，要求明确处理。
- 删除路径不删除共享站点。删除站点前列出相连路径和任务链；没有依赖可删除，有依赖须调整或显式确认允许的草稿级联范围。
- 与正在执行任务或在用发布版本有关的变更不得直接级联到运行数据。历史执行记录与发布快照保留。
- 删除地图先检查设备、执行中任务与模板引用；历史归档与物理清理由管理员维护流程区分。地图名称是否释放由明确的“归档/删除”状态定义；建议归档保留名称、删除释放名称，并允许恢复时重命名。
- 唯一性不能只做“查询后插入”。需设计活动名称注册/数据库唯一约束，在同一事务内释放或占用；SQLite 与 MySQL 分别验收，不使用简单 `(名称, isDelete)` 唯一键，以免第二次同名删除又冲突。
- 删除影响分析、实际变更、引用更新、版本检查与审计记录在统一事务中完成。不可恢复的文件清理另走明确维护操作。

## 实施顺序与迁移

1. 数据盘点与备份：分别导出真实旧表、新地图文档和发布历史，列出重复、孤立及地图归属不明的数据。禁止把 mock 快照当迁移输入。
2. 界面与数据源统一：取消自动快照降级，先做按地图的真实只读列表，再接入共用草稿服务的增删改。完成前不把旧表数据强行混入新主页。
3. 删除与引用约束：新增删除影响检查、稳定 ID、活动名称规则；补充事务、并发和多次删除重建测试。
4. 旧数据迁移：明确可唯一匹配的地图 ID 后迁移，保持旧 ID→新 ID 对照。模糊归属放入“待确认旧数据”，由用户确认，不猜测归属。迁移可重复运行而不重复导入。
5. 验收后切换入口，保留可回滚的数据备份、迁移报告和旧只读记录。验证之前不删除旧表或地图文件。

## 必须通过的验收

- A/B 两张地图使用相同编号，查询、修改和删除互不影响。
- 删除路线后，共享站点和其他路线保留；引用中的站点不能静默删除。
- 同名站点至少连续创建→删除→重建三轮；恢复冲突和并发新建有明确结果。
- 旧任务链引用已删除站点，即使新建了同名/同编号站点，也不能自动重新生效。
- 快速切换地图不会显示旧请求数据；刷新、搜索、分页、导入导出都保持地图范围。
- 草稿保存失败、修订号冲突、断网或后端 404 时不显示保存成功，不回退到模拟写入。
- 执行中任务、在用地图版本不受草稿删除影响；历史快照可追溯。
- 空库安装、SQLite 与 MySQL 升级、备份恢复均单独通过。

## 本轮隔离验证

使用独立 SQLite 内存库直接调用现有站点业务接口，验证了：同图有效名称冲突返回 409、跨图同名允许、被有效路线引用时删除返回 409、路线逻辑删除后可解除引用限制、站点逻辑删除后同名重建成功。另已复现已删除地图仍占用名称。这些是代码与隔离库证据，不代表已检查业务 MySQL 或实车状态。
